## Why one-fix differed from the pilot

Pilot ledger: `/tmp/ab-pilot-fix1-preapproved-live3.jsonl`; evidence: `/tmp/crew-prompt-ab-1794809573653-78446/1-B-delegate-one-fix/`.
Both runs used B, `magpie/auto/deepseek-v4.1-flash`, and product commit `3c0f25c75f77689bfbf79349149cbe2abae6d1a7`.

Pilot children `cnv_2ea5be84` and `cnv_813d7fdd` both have `utils/format.js` in request and worker tools. Sanity child `cnv_cbd5603e` instead receives only `probe`; `cnv_237484cc` receives the scoped fix request. The pilot passes attribution; sanity does not. This is a difference in model-generated dispatch content, consistent with nondeterministic model behavior, not evidence of early settling. Neither ledger has an unfinished run in this cell. Sanity complete events are `[1794811111000,1794811021000]`, final reply is `1794811119530`; pilot events are `[1794809698000,1794809636000]`, final is `1794809715810`. Both satisfy the strict ordering gate. No seed-controlled repeat was performed, so the source of model variation is not experimentally isolated.

The attribution rule stays intact. It prevents an unscoped/decoy delegation or lead-only artifact work from masquerading as successful delegated execution. The current contract requires every delegation to map a declared artifact to tool evidence in that same child, and every required target to be covered. `probe` provides no artifact/acceptance target, so this sample does not justify exempting it. This rule does **not** require writes: a read-only verification worker passes when its request and tool activity identify the same file. The observed rejection is not “the second worker did not write a file”: the unmapped request is the first delegation, and both workers do have file activity.

## Parallel startup and the observability gap

`1-B-delegate-parallel-two/service.log` records:

```text
runId: 'run_a0bde045'
data: {
  errorName: 'AgentRunError',
  errorCode: 'conflict',
  cause: 'Crew 资源尚未分配'
}
```

The fixture log shows `dlg_c626557c` approved with resource state `queued`; another delegation is already using the same directory scope. Fixture scopes include shell/file_read/file_write for both workers. The startup guard at `src/domain/agent-run.ts:588` rejects an unallocated resource. Calling request, approval and allocation atomically cannot guarantee allocation under contention. `LIVE-PILOT-FIX1.md` already limits the prepared fixture to non-general contention handling. The evidence establishes a resource-readiness startup rejection; it does not establish a provider/model failure or pinpoint the entire scheduler race.

The product service log is informative, but the durable run/domain evidence collapses its specific error into a generic `run_failed` and message. That is a product observability gap at the durable evidence boundary. The harness now retains the product-provided `errorCode` and `errorMessage`, plus run identity/status/start time, in the ledger; it does not invent a more specific domain error. Diagnose this saved case using `service.log`. No product guard, scheduler, or error handling was changed. Ignoring the failed run, waiting for it to disappear, or counting incomplete delegations as model failure would obscure the execution anomaly.
