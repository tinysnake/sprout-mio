# Machines：核心范围与决策记录

状态：讨论中。本文记录已确认的产品决定，不代表实现已经完成。分期以 core-scope.md 为准：未标注二期或未来方向的能力属于一期；二期明确要做，未来方向时间未定。

参考：原 Sprout issue #265（Lease escrow）。本轮明确决定优先于旧 issue；尚未讨论的旧要求不自动纳入第一版。

## 已确认的核心

### 远端执行

- Machine 只需运行 sprout-worker，不要求安装任何 agent harness。
- Agent harness 运行在其他位置，通过 harness 扩展或 MCP tools 与 worker 通信、操作 Machine。
- 远端工具必须核验调用分身所属 Project、Machine 是否加入该 Project，以及该 Project 内的有效持有租约。
- 访问 Machine 现场时，只读确认、源码读取与环境排查也遵循租约规则。DM 可以直接取得租约排查，不要求先创建 Task；一个分身可同时取得多台 Machine 的租约以比较现场差异。
- 日常仓库问题可通过 Project 的宿主侧仓库入口处理，无需占用 Machine；该入口不替代 Machine 的实际文件、依赖或进程现场，第一版不增加免租约的远端只读通道。
- 持有对应项目有效租约后，Agent 可以使用 worker 所属用户的权限操作整台 Machine，包括 shell、文件和进程。工作目录是默认位置，不是访问边界。
- Project 硬隔离限定在 Sprout 数据、上下文和授权层；Machine 内的文件、进程、端口与资源共享由 Project organization 负责，Sprout 不为共享 Machine 提供项目级操作系统隔离。

### 第一版操作能力

- 第一版提供 shell、文件和进程操作，支持执行命令、修改文件、安装依赖、启动应用和构建。
- 截图、鼠标和键盘等图形桌面工具属于未来方向，实施时间未定，不承诺二期。

### 第一版：长时间执行与恢复查询

- 构建等长命令可以在 Machine 上持续执行，不依赖发起它的某次 agent run 一直存活，也不因宿主与 Worker 的连接中断而自动终止。
- 每次执行有稳定、可查询的标识，后续 run 可以查看日志、当前运行状态和结束后的退出结果。连接中断或状态无法确认时明确表示未知，不误报为执行完成。
- 连接恢复后，具有当前有效持有租约的分身可以继续查询和管理已有执行；租约交接后，新持有者也可以凭执行标识接续，原持有者不能凭旧标识绕过租约授权。
- 请求超时或响应丢失后，可以确认原请求是否已启动执行，并在重试时避免重复启动同一命令；状态不确定时不能直接假设命令未执行。
- 此能力属于远端 shell、进程工具的基础要求；租约与进程生命周期继续独立，租约动作不自动终止已有执行。
- 执行标识和请求去重方式、日志与结果保留，以及 Worker 或 Machine 重启后的恢复范围留待技术设计。

### 操作系统范围

- 一期支持并验收 macOS Worker，包括 shell、路径、进程和长命令行为。
- 二期明确补齐 Windows Worker，验证对应的平台行为，最终支持 macOS 与 Windows。
- macOS 与 Linux 尽量复用适用的 Unix 实现；Linux 验收范围未定，不自动纳入一期或二期。

### Agent profile 与分身

- Agent profile 定义人设与配置。
- 一个分身由 Agent profile × Chat 唯一确定。每个 profile 在同一段对话中最多有一个分身。
- 同一段对话的多轮运行属于同一个分身；运行结束或服务重启不改变分身身份。
- 不同对话中的分身是独立个体。即使来自同一个 profile，也不能共享或代用彼此的租约。

### Project 成员关系与独占范围

- Machine 加入 Project 后，才向该 Project 的 Agents 提供查询和租约申请。
- 同一台物理 Machine 可以加入多个 Projects；各 Project 的 Machine 列表、租约和协调信息相互隔离。
- 租约互斥单位为 Project × Machine。一期同一 Project 内一台 Machine 由一个分身持有；二期挂靠状态也保持占用。不同 Projects 可以在同一物理 Machine 上持有独立租约。
- 其他 Project 的持有、挂靠或收回不改变本 Project 的租约，不作为本 Project 申请失败的占用依据，也不向本 Project 的 Agent 暴露。
- 不跨 Project 统一分配、协调或仲裁物理 Machine。多项目并行使用引起的文件、进程、端口和资源冲突由 Project organization 负责。

### Machine 移出 Project

- 没有本项目租约时，Human 可以直接将 Machine 移出 Project。
- 有本项目内被分身持有的租约时，先警告 Human；确认强制移除后，撤销该项目在此 Machine 上的租约及操作权，不要求先逐项手动释放。二期新增的挂靠租约也按此规则处理。
- 移除后，该项目不能继续申请或认领此 Machine 的租约，也不能凭旧租约继续操作。
- 受影响的正在运行的 agent-runs 收到明确的资源撤销通知，自行决定换 Machine、继续其他工作或结束；不因 Machine 移除而一律强制中止 runs。
- 无法确认撤权成功时，保留对应的待处理占用并交由 Human 处理，不能显示处置成功或将旧占用视为已经释放。
- 文件与进程保持独立生命周期，不自动删除或终止；其他 Projects 的成员关系与独立租约不受影响。

### 租约生命周期

- 一个分身可以同时持有多台 Machine。
- 正常申请和释放租约的角色是 Agent 分身。
- 占用持续到明确释放。等待反馈、掉线或超时不自动释放租约。
- 允许同一分身跨 run 保留租约。正常结束前，指令软性要求判断应保留、直接交接还是释放；二期增加挂靠选项。不强制调用租约工具才能结束，不增加专门的模型收尾轮次。
- 正常 run 结束未改变租约时，系统保留现有持有关系；异常退出或操作结果不确定时，不静默释放或转授给他人。
- 分身可以主动申请本 Project 内空闲 Machine 的租约，或接受持有者直接交接；二期再支持认领符合条件的挂靠租约。空闲只指本 Project 的租约状态。

### Machine 选择

- Agent 查看当前 Project 的机器列表、说明和项目内占用状态，自行申请一台具体 Machine。
- 一期不提供系统自动资源协调。Machine 忙时返回占用和持有者，由 Agent owner、持有者或 Human 通过对话协调，申请者可以换一台或等待；空闲分身的租约不因此失效。
- 第一版不提供按能力自动匹配和分配 Machine 的调度机制。
- 当前 Project 内的分身可以申请该 Project 已加入且项目内空闲的任意 Machine，不另设按 Agent 区分的 Machine 访问名单。未加入当前 Project 的 Machine 不提供给该项目 Agents。
- 二期挂靠中的租约只允许符合领取范围的分身领取。

### 一期：直接交接

- 当前持有者可将租约直接原子转给指定、有本 Project 参与权的分身；不跨 Project 交接。
- 交接成功前由原持有者持有，成功后原操作权失效、新持有者取得操作权，全程保持 Project × Machine 占用，不经过释放给其他工作的空窗。
- 尚无明确接手者时原分身继续持有，不创建挂靠中间状态；需要释放时明确释放。
- 交接不改变文件和进程状态，新持有者可按有效租约查询和管理已有执行。

### 二期：挂靠与领取

本节为二期承诺，一期不实现挂靠状态或领取流程。

- 持有者可以将租约挂靠到当前 Project 的一个 Group，或 Group + 指定 Agent。Public Channel 是特殊 Group，同样支持挂靠；不能跨 Project 挂靠或领取。
- 二期不支持将租约挂靠到 DM。DM 展示其唯一 Agent 分身持有的 Machines 和租约状态；同一分身跨 run 续做无需为此挂靠和重新领取。
- Group + Agent 指向该 Group 中对应 profile 的唯一分身。
- 挂靠期间 Machine 保持占用，原持有者交出操作权。
- 只有该 Group 内符合指定条件的分身，才能凭自己的身份领取租约。
- 成功领取后，领取者成为新的持有者，可以继续使用、挂靠或释放。
- 交接期间不会把 Machine 释放给无关工作。
- 挂靠不改变 Machine 上的进程状态。领取者获得 Machine 操作权后，可以查看和控制原有进程。
- 原分身挂靠后不能继续向 Machine 下命令。远端进程可以持续运行，agent harness 本身不在 Machine 上，不属于交接对象。

### 租约与进程独立

- 租约只决定 Machine 的占用和操作权，不管理进程生命周期。
- Agent 负责在释放前进行适当清理。
- 直接交接和释放本身不触发进程清理，也不以进程全部结束作为条件；二期挂靠、领取同样遵守此边界。
- 文件、未提交改动和构建产物不会因为租约释放而自动删除。

### 人类强制收回

- 人类必须拥有强制收回租约的权限；收回针对一份 Project 内租约，不能一并撤销其他 Projects 在同一物理 Machine 上的独立租约。
- 该权限用于 Agent 掉线或分身无法继续工作的情况；二期也用于挂靠无法接续。
- 强制收回撤销旧操作权；进程清理是独立动作，不由租约释放自动触发。离线 worker 重连后的授权同步细节仍待确定。
- 一期移除 Agent 前要求手动停止 runs、处理租约和责任，不能用强制移除一并善后。二期 Human 确认强制移除 Agent 后，中止其本项目活动 runs、撤销各分身操作权；确认旧操作权撤销后自动释放租约。
- 无法确认撤权成功时，保留对应租约占用并交由 Human 处理，不能提前显示为空闲。文件和进程仍按独立生命周期保留，不随租约释放自动清理；处置不影响其他 Projects 的独立租约。

## 二期：申请遇阻时自动协调

本节为二期承诺，一期由 Agent owner 或 Human 通过对话协调，不提供此系统流程。

- 协调仅在当前 Project 内进行，候选 Machine、持有者、请求、结果与通知均不跨 Project。其他 Project 持有同一物理 Machine 的租约不触发本项目协调。
- 申请者明确需要接手某台 Machine，但租约仍被其他分身持有时，可以请求该持有分身处理交接。
- 申请者需要 Machine、但全部被占用时，系统优先向空闲持有分身请求归还或交接；选择协调对象不承诺提供能力匹配调度。
- 请求作为明确的资源协调事件送达当前持有分身，不依赖小脑/JEV 从普通聊天中推断唤醒。空闲时唤醒，运行中送入当前轮，继续保持单分身串行。
- Harness 在 Machine 之外运行，查询占用和作出协调决定不需要先取得空闲 Machine。
- 持有者可以释放、按现有规则挂靠交接，或说明仍需保留的原因。空闲不等于无效占用，不自动抢占。
- 同一租约同时只处理一个协调请求，重复申请合并；处理时重新检查当前持有关系，旧请求不能改变已交接的新租约。
- 每次申请只自动协调一轮，逐个尝试且次数有限，不广播唤醒所有 Agents，不形成自动催促循环。
- 交接仍受现有领取范围和身份授权约束；释放后申请者需要重新申请，不保证优先获得该 Machine。
- 持有者明确仍需保留时，申请者换目标或等待；所有 Machine 都确实需要保留时，返回容量不足。
- 无法响应、模型调用失败或操作状态不确定时，转交 Human 处理；不因此自动释放租约。
- 资源协调由租约与沟通机制执行，Info Hub 聚合请求、处理结果及保留原因。

## 待收敛

- 一期直接交接、强制收回及异常退出后的授权确认细节。
- 二期协调请求的等待时限、有限尝试次数及与人类暂停自动唤醒的配合。
- 原 Sprout 的实现与分期前的讨论见 [run 与租约分析](lease-run-analysis.md)；该文不覆盖本轮分期决定。

## 二期：挂靠超时提醒（选项 B）

- 挂靠长期无人领取时，提醒人类处理。
- 人类决定如何接续或收回。
- 超时本身不释放租约。
- 提醒时限、重复提醒及呈现位置尚未确定。

## 二期：挂靠超时后的 owner 协调（选项 C）

这是明确在二期实现的能力，不纳入一期：

- 挂靠超时后，由系统通知或唤醒 Group owner 协调处理。
- Group owner 无法处理或未响应时，进一步提醒人类。
- 自动协调也不能因为超时自行释放租约。
- 具体裁决权限、重试和升级规则留待后续设计，不直接继承旧 issue 的全部细节。
