# 个人助理与 channel 决策草案

> 状态为产品讨论草案。本文记录个人助理、会话和 channel 的共同边界。身份核验细节、授权策略及完整首期交付范围尚未冻结，本文不表示能力已经实现。

## 讨论状态与来源

本文根据本轮产品讨论及 Human 提供的语音助理设计材料整理。语音材料中的候选框架和完整通知策略不自动成为首期任务。首期授权模式以本文记录的已确认决定为准。

状态与[自动化草案](automation-decisions.md#讨论状态)一致。**已确认**表示已经接受的产品方向，**建议**表示尚待确认的默认方案，**待定**表示仍需要决策。现有实现与验收继续以[开发总计划](development-plan.md)及[一期归档](archive/phase-one/README.md)为准。

## 已确认的产品方向

个人助理以 Human 为中心。Human 可以通过助理了解多个工作对话的进展，讨论调整，再把经过授权的请求交给工作 Agent。工作 Agent 执行期间，助理仍能回应 Human。

个人助理具有以下边界。

- 助理与执行工作的 Agent 分身分开，助理对话不直接占用某个工作 Chat。它们复用 Agent 与 Chat 的基础模型，助理 Chat 同样归属 Project，具体边界见下文。
- Sprout 内提供原生的助理对话入口，交互类似与 Agent 的 DM，不依赖飞书或语音才能使用。
- 助理可以关注多个有权访问的 Projects、Chats 和 Agents，不因接入飞书而固定为某个工作 Chat 的遥控窗口。
- 助理可以没有绑定的 channel，也可以绑定多个 channel。没有连接时，会话和待通知事项仍可保留。
- 语音聊天也是一种 channel。飞书、Web 文字和实时语音可以成为不同入口。
- 助理、会话与连接各有自己的生命周期。断开入口不隐式删除会话。明确绑定到同一助理 DM 的入口共用历史与上下文，不同 DM 的历史不自动合并。
- 助理的回复与主动通知统一分发到消息所属 DM 当前可发送的所有已绑定 channel，来源不决定回复去向。
- 观察和执行分开。助理查询事实、提出建议，经受控委派能力影响工作，不直接取得普通工作 Agent 的全部工具。
- Channel 接入必须模块化，先实现飞书。初版 channel 只接私聊 DM，不接外部群聊。语音先确定共用边界，实际 STT、TTS 和实时交互在后续范围中安排。

没有 channel 不表示模型需要一直运行。观察任务、模型调用和入口连接如何启动与停止，需要在运行契约中分别定义。

## 个人助理与现有术语的关系

现有 Chat 是 Project 内的持久协作单元，包括 DM、Group 和 Public Channel，见[术语表](glossary.md)与[通信决策](communication-decisions.md)。本文的 channel 表示人与助理交互的接入通道。它与 Public Channel 是两个概念，不能共用身份、成员或生命周期语义。

现有工作 Agent 的持续分身由 Agent profile 与 Chat 确定。个人助理不能通过选择同一个 profile 就自然取得跨 Project 的观察与操作能力。

### 原生入口与普通 Agent Chat 的复用

**已确认。** 助理在 Sprout 内需要可直接访问的对话入口，能发送消息、查看历史和继续交流。助理 Chat 与其他 Chat 一样归属 Project，外部 channel 断开不影响该入口保留助理会话。

**已确认。** 复用普通 Agent Chat 的消息、历史、输入、运行状态和停止能力。助理以受控的 Agent 身份或能力配置表达，不新增一种 `assistant` Chat 类型，不另建一套助理消息历史。这里的“独立助理会话”指它有自己的 Chat、上下文与 Agent 分身，不表示必须实现另一套聊天系统。

需要分别建模以下问题。

| 维度 | 个人助理的表达 |
| --- | --- |
| 对话形式 | Human 与 Agent 的 DM，复用现有聊天基础 |
| Chat 归属 | 与其他 Chat 一样属于一个 Project，不新增个人作用域或脱离 Project 的 Chat |
| 查询范围 | 通过受控接口查询当前 Human 有权访问的 Projects，与 Chat 的归属分开校验 |
| Agent 能力与执行身份 | 独立的助理 Agent profile，模型和 effort 单独配置；程序限定助理工具集合，支持观察、watch、提案及获准委派，不直接执行工作 |

现有 [`createDirectChat`](../src/domain/chat.ts)要求 Project 归属和项目 Agent 成员，助理沿用这一归属模型。持续分身仍由 Agent profile 与 Chat 确定。助理的跨 Project 查询通过受控观察接口校验当前 Human 的权限，不改变 Chat 的 Project，不放宽普通工作 Agent 的项目权限。委派到其他 Project 时，目标工作 Agent 仍在目标 Project 的既有执行范围内工作。

`jobTitle` 仍是显示标签，人设提示词也不授予权限。助理运行时应由程序选择受限工具集合，并由后端在每次查询和委派时校验权限；不能直接继承普通工作 Agent 的完整工具配置后只靠提示词限制。

Sprout 内的对话展示与外部 channel 使用同一份助理消息。建议先持久化消息，再由投递层分发到该 DM 当前可发送的已绑定 channel；Web 展示原有消息，不为每个 channel 另生成一份回答。外部输入去重及分发回声防护在业务契约中落实。原生入口在导航中的位置、助理 Chat 所属 Project 的选择及 Agent 能力配置字段尚未冻结。

### Channel 与助理 DM 的绑定

**已确认。** 接入飞书或语音时，选择一个 Project 下的助理 DM 作为该入口的绑定目标。绑定后的输入进入这段 DM，Sprout、飞书和语音等绑定到同一 DM 的入口共用该 DM 的历史与上下文。助理在该 DM 中产生的回复和主动通知，统一分发到这段 DM 当前可发送的所有已绑定 channel，不分来源。

身份绑定与 DM 绑定分别表达外部说话者是谁、消息进入哪段对话。选择目标时仍需检查 Human 对所属 Project、DM 及助理身份的访问权限。仅因两个入口属于同一 Human，不会自动绑定到同一 DM，也不会把所有助理 DM 的消息向全部 channel 广播。

连接断开或解绑不删除 DM 历史。绑定到新建 DM、切换已有目标的具体操作、历史消息补发，以及绑定无效时的处理在后续契约中落实，不凭最近使用的 Project 或 Chat 隐式改选目标。

**已确认方向。** 飞书身份绑定只说明外部说话者对应哪个 Human。身份对应不等于授权全部操作，助理也不继承该 Human 的所有权限。

### 独立 Agent 与响应配置

**已确认。** 助理使用独立的 Agent profile，模型和 effort 可以针对助理单独定制。助理面向即时交流，配置选择优先考虑交互响应需求，与执行工作的 Agent 分开配置。具体模型、默认 effort 和响应目标尚未冻结，不预设必须使用某个模型或固定低 effort。

助理仍使用普通 Agent 的配置与分身基础，Chat 仍归属 Project，持续分身仍由 Agent profile 与 Chat 确定。独立 profile 同时承载程序可识别的助理身份或能力配置，运行时据此加载受限工具集合；模型选择不改变权限边界。能力字段与具体运行配置在业务契约中落实。

## 讨论中的对象关系

这些关系用于界定产品，不预设数据库表、API 或某个接入 SDK。

| 对象 | 责任与关系 | 状态 |
| --- | --- | --- |
| 个人助理 | 服务于 Human，由独立 Agent profile 承载；单独配置模型与 effort，负责交流、观察、提案和获准的委派 | 独立 Agent 及模型、effort 单独定制已确认 |
| 助理会话 | 保存当前交流上下文，可引用多个工作对象；是归属 Project 的普通 Agent Chat，与执行工作的 Chat 分开 | 普通 Chat 复用、Project 归属及原生入口已确认 |
| Channel adapter | 处理平台认证、接收与发送，转换成助理可处理的输入输出 | 已确认 |
| Channel 连接 | 表达入口是否可用，生命周期独立于助理和会话；不以连接状态代替 Human 身份 | 已确认方向，连接与绑定的具体关系待定 |
| 身份绑定 | 将平台中稳定的用户身份关联到 Human；首期每个 Human 最多绑定一个飞书账号，绑定本身不授予全部工作权限 | 账号数量、绑定、解绑和换绑流程已确认，身份核验细节待定 |
| 会话接续关系 | Channel 接入时明确绑定到一个 Project 下的助理 DM，同一 DM 的入口共用历史与上下文 | 绑定目标与共享上下文已确认，新建及切换操作待定 |
| 提案 | 记录助理建议的目标与具体操作，供程序检查及 Human 确认 | 已确认方向，字段与状态待定 |
| 委派记录 | 关联获准请求与实际工作对象，区分评估和执行 | 已确认方向，字段与状态待定 |
| 关注关系 | 记录 Human 明确关注的工作 Chat，由服务端保存与调度；独立于单次 run 和 Pi 进程 | 持续关注语义及 watch 接入分工已确认，具体契约待定 |
| 通知 | 保存需要告知 Human 的事实，并区分发送、播放与 Human 确认 | 范围、四类通知及默认汇报节奏已确认，保存策略待定 |

同一个 Human 的不同入口不会仅凭身份相同就共享全部会话内容，只有明确绑定到同一助理 DM 的入口共用该 DM 的历史与上下文。同一个入口的接续或新建会话也不删除工作 Chat 的历史。

**建议。** 首期每个 Human 提供一个默认助理。可配置多个助理、复杂路由与独立人格不作为初始结构的前置条件。助理模型与 effort 单独配置已经确认，人设提示词的可配置范围、默认助理的创建及选择流程仍待确定。

## 身份与授权的边界

**已确认。** 首期每个 Human 最多绑定一个飞书账号，也可以不绑定。同一 Human 同时绑定多个飞书账号不在首期范围。

绑定与撤销采用以下流程。

1. **绑定。** 从已登录的 Sprout Web 发起，再由飞书侧确认。
2. **解绑。** 生效后立即停止通过该绑定接收指令和发送通知。保留助理会话与历史，不自动停止已经启动的工作。
3. **换绑。** 先解除旧绑定，再绑定新账号。

这些是已确认的产品行为。具体身份键、核验方式与撤销生效的程序检查仍需在业务契约中落实。

现有 [`access.ts`](../src/domain/access.ts)区分 Human 的 Project 归属访问与工作 Agent 的执行范围。即使工作 run 由人类消息唤起，执行时仍受工作分身的范围约束。新增助理不能只携带 Human 的 `userId` 就绕过这些限制。

**已确认方向。** 助理需要独立、受程序限制的访问边界。观察时只能读取获准范围，执行时只能通过明确的委派入口提交获准操作。只靠提示词要求“不要越权”不满足这一边界。

**已确认。** 第一版助理默认可以查询该 Human 当前有权访问的全部 Projects，不要求逐个 Project 授权。具体内容仍受现有可见性规则约束，查询时以 Human 当前权限为准。查询范围、主动通知范围和工作变更授权分别确定。

**建议。** 有效的操作范围同时受以下条件约束。

- 当前说话者已认证为哪个 Human。
- 该 Human 对目标 Project 和工作对象仍有权限。
- 该助理被允许观察或委派哪些对象及操作。
- 当前会话模式和本次提案是否要求确认，以及确认是否仍有效。

平台事件认证与 Human 身份绑定是两步。验证飞书事件来自受信平台，不代表事件中的任意用户已经有权控制 Sprout。平台应用凭据、连接和 Human 绑定分别表达，不假定一条平台连接只服务一个 Human。

语音入口依赖已登录的用户、设备或连接建立身份。语音识别出的姓名和指令文本不作为身份凭证。

## 群聊与信息接收范围

**已确认方向。** 群不是一个 Human。群内不同说话者的身份和权限需要分别处理，不能把整个群映射成同一个拥有者。

群内回复还涉及谁能看到内容。请求者有权读取某个 Project，不等于当前群内所有成员都有权看到该 Project 的状态。助理不能把个人会话内容、跨项目细节或私密通知默认回发到群里。

**已确认。** 初版 channel 只接私聊 DM，不接外部群聊。飞书首期仅支持 Human 与助理的私聊，不接收群内消息、群内 @ 或向外部群投递助理消息。外部群聊接入留到后续范围。

这不会限制助理在 Human 当前权限内查询、watch 或委派 Sprout 内部工作 Group。外部群聊接入与内部工作 Group 不自动建立成员映射，也不按默认规则拆出每人一个工作 Chat。后续若支持外部群聊，需要另行确定说话者绑定、允许的操作和群内可见内容。

## 观察事实与会话上下文

**已确认方向。** 助理通过结构化信息了解当前工作。可以报告工作是否忙碌、已发生的工具调用、耗时、错误和结果，但不能编造 Agent 的思考过程。

现有 [`protocol.ts`](../src/server/pi-host/protocol.ts)、[`agent-run.ts`](../src/contracts/agent-run.ts)和 [`run-activity.ts`](../src/server/pi-host/run-activity.ts)提供可复用的运行事实。它们不直接构成跨入口、持久化的助理通知收件箱。

助理按需查询持久历史和当前状态。会话上下文可以在一段时间后重新开始，不能要求模型永远保留完整工作历史才能正确回答。

**建议。** 初期读取最近一段消息并支持继续查询。语音材料提到最近约 50 条消息，可作为调查起点，不冻结为 API 上限或永久记忆策略。

工作状态变化可以产生通知候选。第一版主动通知只覆盖助理委派或 Human 明确要求关注的工作，包含结果事件与 run-activity 定期汇报。默认汇报间隔为 5 分钟，允许 Human 调整，具体合并方式仍待确定。默认能查询全部 Projects 不表示自动推送全部 Projects 的活动。

## 持续关注与 watch 接入

**已确认。** 助理可通过 Pi extension 暴露的 watch 工具，请求关注某个有权访问的 DM 或 Group。Extension 是接入入口，Sprout 服务端负责检查 Human 当前权限、保存关注关系、定时读取状态及 run-activity，并处理取消关注和权限撤销。模型调用工具不产生额外读取权限。

关注状态与定时触发不只放在 extension 进程内，不依赖某一轮助理 run、Pi 进程或 channel 连接持续存活。助理会话可保留，模型进程按需启动。现有工作 run 收尾会关闭 Pi runner，这也是持续关注必须独立保存的实现依据。

**已确认。** 关注 Chat 表示持续关注该 Chat 后续的工作，直到取消关注或失去权限。某个 run 结束，只停止该 run 的周期汇报，不删除 Chat 的关注关系。一个 Group 可以包含多个工作 Agent 与 run，不能把 Chat 与单个 run 当成同一个观察对象。助理委派的工作默认纳入通知范围，但不因此自动扩大为对整个 Chat 后续工作的持续关注。

服务端生成汇报时，可直接使用结构化数据生成模板，或将活动摘要交给助理组织语言。Pi 的 `sendMessage` 可作为自定义事件进入助理上下文的桥接方式；`appendEntry` 用于保存 extension 数据，不进入模型上下文，单独调用不会触发汇报。具体消息投递模式和宿主协议在实现前核对实际 SDK。

后台活动保留事件来源，不伪装成 Human 指令或确认。事件交给个人助理，不唤醒被关注的工作 Agent，也不改变其正在执行的任务。关注目标、频率、取消操作及消息桥接的具体 API 尚未冻结。

## 提案、确认与委派

**已确认方向。** 助理默认不持有 shell、文件写入或进程控制工具。需要影响工作时，通过受控入口向工作 Agent 提交请求。即便复用 Pi runtime，也要由程序限制工具集合和操作权限。

提案确认绑定具体目标和具体操作。提案内容、目标或授权发生变化后，旧确认不能无条件用于新的请求。执行前仍需检查当前权限，不把过去的一次确认视为永久授权。

语音材料提出三种会话模式，保留为设计输入。

- **保守模式。** 助理提出建议，Human 确认后请求工作 Agent 评估，再由 Human 确认执行。
- **询问模式。** 具体提案经过 Human 一次确认，再提交执行。
- **激进模式。** 在预先授予的操作范围内自动提交，范围之外仍需要确认。

**已确认。** 首期采用询问模式。查询进度和读取状态直接进行，不要求额外确认。需要改变工作时，助理先给出具体目标和操作提案，Human 确认一次后，再通过受控入口交给工作 Agent 执行。目标或操作变化后，需要重新确认。

**已确认。** 首期支持在 Sprout 和飞书内直接确认工作提案。提案展示明确的目标和操作，Human 在任一入口确认一次即可经受控入口提交执行。同一提案在多个入口重复确认，程序只产生一次工作提交；目标或操作变化后重新确认，执行前再次检查当前权限。未来语音接入时复用同一份提案及确认记录。

确认有效性与重复提交检查由服务端执行，不把模型声称“Human 已确认”当作有效授权。具体提案展示、确认输入方式、记录字段与并发去重在后续契约及交互设计中落实。

保守模式的评估与二次确认、激进模式的授权范围内自动执行留到后续。首期不同时实现三套交互。

评估与执行必须是两个不同目的。工作 Agent 的评估回复不自动触发执行。评估或实际工作异步进行时，助理会话仍应能继续回应 Human。

**建议。** 委派只承诺已接纳及可追踪的工作关联。目标忙碌、被移除、归档或权限失效时，显示对应结果，不能将“已提交”说成“已经开始执行”或“已经完成”。

## Channel adapter 与飞书首期

**已确认方向。** Adapter 负责接入平台，助理核心负责理解、观察、提案和汇报。平台 SDK 类型不应成为助理会话和委派的业务身份。

**建议。** 初期使用静态注册的 adapter，不建设运行时插件市场。为未来平台保留共同输入输出边界，但不强求所有平台支持语音、线程、卡片或相同的确认界面。

飞书首期方向为文本交流、查询进度、返回结果与 Web 链接。工作期间助理仍能回应。自然语言指令需要走助理的身份与授权机制，不能直接映射为任意工作 Agent 工具调用。

**建议。** 优先调查企业自建应用的长连接接入，减少对公网回调入口的依赖。实际 SDK、凭据管理、权限范围及重投行为在实现前核验，不把“无需公网回调”理解为“无需互联网”。

入口收到消息后，工作执行不占住平台事件处理过程。平台事件的去重与投递策略应保持轻量，并说明首期不保证哪些恢复场景。

## 语音 channel 的专属责任

**已确认方向。** 实时语音可以接入同一个个人助理，复用身份、观察、提案、委派和通知边界。STT、TTS、轮次判断、回声处理、打断与播放状态由语音 channel 处理。

语音打断、停止播放、取消助理回答和取消工作 Agent 的执行是不同操作。后续语音契约需要分别定义，不能把停播当成撤回已批准工作。

语音技术选型、端到端延迟、设备支持、模型成本和打断恢复暂不进入本轮开发排期。共享边界在飞书路径中验证后，再补语音的专属契约与页面交互。

## 通知与多个入口

**已确认方向。** 工作事实、通知内容、发送结果和 Human 确认分开。发到飞书不等于 Human 已阅读，语音已播放也不等于 Human 已确认。

**已确认。** 第一版主动通知只覆盖助理委派的工作，以及 Human 明确要求它关注的工作。Human 从 Web 或其他入口安排的工作不自动进入该范围，但可以通过明确关注纳入。仅查询一次进度不等于要求持续关注。所有查询和通知仍受 Human 当前权限约束。

**已确认。** 助理的消息统一向消息所属 DM 当前可发送的所有已绑定 channel 投递，与请求来自哪个 channel 无关。该规则同时适用于普通对话回复、提案、查询结果和后台主动通知。语音与飞书都可发送时，从语音发起的查询结果也同时发到飞书，从飞书发起的请求回复也同时通过语音输出。Human 无需每次请求或关注时指定回复位置。

来源信息用于身份校验、上下文与追踪，不用于限制输出目的地。多端投递使用同一条助理消息，各 adapter 按平台能力呈现为文字或语音。Channel 明确绑定到 Project 下的助理 DM，输入共用该 DM 的历史与上下文，输出向该 DM 的可发送入口分发，见[DM 绑定规则](#channel-与助理-dm-的绑定)。其他 DM 的历史不会自动合并；初版只接私聊 DM，外部群聊留到后续，见[群聊与信息接收范围](#群聊与信息接收范围)。

“可发送”由程序根据当前绑定与 adapter 的发送能力判断。服务端分别向可发送的 channel 投递，并分别记录结果；某个 channel 发送失败不阻止其他 channel 发送，也不重跑工作或让模型重新生成同一答复。没有可用 channel 时保留消息记录。不可用入口重连后的历史补发策略仍待确定。

**已确认。** 首期主动通知包括四类，均受已确认的工作关注范围约束。

- **工作完成。** 有结果可以向 Human 汇报。
- **工作失败或中断。** 工作无法继续，需要 Human 处理。普通工具报错后已自行恢复的情况不单独通知。
- **需要 Human 决定。** 例如提案待确认、需要补充信息或选择下一步。
- **run-activity 定期汇报。** 对关注范围内正在运行的工作，周期性汇报可观察到的执行活动。

**建议。** 周期汇报概括当前动作、本周期可见的工作记录、持续时间和错误信息，不逐条转发每次工具调用。依据已有 run 状态和 activity 事实汇报，不推测 Agent 的思考过程或未经证实的完成进度。长命令没有新事件时，可以报告当前动作及其持续时间；活动缺失或过时时如实说明。

现有 activity 包含当前步骤、有限条数的工作记录与更新时间，不能视为无限历史或独立通知收件箱。周期汇报是否需要保存快照，以及跨周期怎样识别新活动，在业务契约中落实。

**已确认。** run-activity 默认每 5 分钟汇报一次，允许 Human 调整。长命令没有新事件时，仍简短报告当前动作及持续时间。run 结束后停止周期汇报，完成或需处理的失败另行通知。定期汇报属于助理通知能力，不改变业务 cron 的离线不补做规则。

**已确认的程序分工。** 服务端通知调度负责到期触发，读取 run 状态和 activity，并在投递前检查关注范围、Human 当前权限，以及各 channel 的绑定和发送能力。输出按本节已确认规则分发到所有可发送的已绑定 channel，目的地不由模型按来源选择。run 结束后取消后续周期触发，已在处理中的报告投递前重新核对状态。模型不负责记时，也不能自行增加通知对象或越过绑定范围。持续 Chat 关注与单次 run 汇报的区别见[watch 接入](#持续关注与-watch-接入)。

汇报中的状态、动作、时间和错误字段来自结构化记录。记录中的 Agent 文本应保留为 Agent 的说明，不把它当作程序独立验证的执行结果。模型可辅助组织语言，但自由文本仍可能失实。关键字段应由程序直接呈现；模型生成失败或超时，可使用同一份数据生成简短模板报告。模型调用和发送均不阻塞工作 run，发送失败不重跑工作。

以上通知调度和投递检查尚未实现。当前程序已有运行事件采集及 activity 查询，现有工作续跑调度器也不是个人助理的周期通知服务。具体调度、并发和投递状态在业务契约中落实。

**建议。** 语音忙碌时通知排队，不强行打断说话者。

通知保存期、去重、合并、优先级、过期和已确认标记的具体操作仍待设计。保存通知不意味着为离线期间错过的 cron 补做工作，也不意味着助理必须持续调用模型。

## 用于细化契约的场景

这些场景尚未成为冻结的验收清单，也没有实际执行。

1. 工作 Agent 正在执行长任务。Human 在飞书询问进度，助理查询事实并回应，不等待原任务结束。
2. Human 有权访问两个 Projects。助理无需逐个 Project 授权即可查询两边的进度，明确结果属于哪个工作对象，不自动把两边的历史混为一个工作 Chat。查询仍遵守 Human 当前权限及内容可见性。
3. Human 在 Sprout 或飞书看到具体目标和操作提案，在任一入口确认一次后，工作 Chat 接纳请求；Human 尚未确认时不提交执行。同一提案跨入口重复确认只产生一次工作提交。助理分别报告接纳、执行和完成事实，能追踪到实际工作。
4. 提案在确认后改变，或执行前权限被撤销。旧确认不能授权新的操作。
5. 飞书断开后，会话与待通知事项仍存在。重连或接入语音后，后续助理消息按当时可发送的绑定 channel 分发；历史会话接续与离线消息补发分别定义，不因多端投递自动合并其他会话历史。
6. 助理没有 channel 时保留关注配置与必要记录。消息不会误发到其他 Human 或未经授权的外部群。
7. 同一 Human 将飞书和语音绑定到同一个 Project 下的助理 DM，两者当前均可发送。从任意一端发起请求后，输入进入同一 DM，助理生成一份答复并向两端投递。Human 在 Sprout 打开该 DM 可查看并继续同一段对话。某一端不可发送时，仍向另一端投递。
8. 工作已完成而通知失败，重发通知不重跑工作；未来语音停播也不隐式取消工作。
9. Human 解绑飞书后，该绑定不再接收指令或发送通知，助理会话、历史和已经启动的工作保留。换绑先解除旧绑定，再建立新绑定。
10. Human 查询从 Web 安排的工作，助理可以回应，但该查询不自动开启主动通知。Human 明确要求关注后，这项工作才进入主动通知范围；助理委派的工作默认在此范围内。
11. 关注范围内的 run 持续执行时，助理按确定的周期汇报实际 run-activity。普通进度可以进入周期摘要，完成、需处理的失败及待 Human 决定事项另按相应通知处理。工作执行与报告生成互不阻塞，生成或发送失败不重跑工作。
12. Human 明确关注一个 Group。某个 run 结束后，其周期汇报停止；该 Group 后续的新 run 仍属于关注范围。助理 Pi 进程退出不删除关注关系，取消关注或失去权限后停止该关注的后续投递。
13. 初版飞书群内消息与 @ 不进入助理 DM，助理消息也不投递到外部群。Human 仍可在私聊中要求助理查询、watch 或委派其有权访问的 Sprout 内部 Group。

## 优先讨论的产品决定

下一轮先讨论以下三组决定，其余技术问题通过代码和候选接入调查解决。

1. **身份核验与入口范围。** 账号数量及绑定、解绑、换绑流程已经确认，见[身份与授权的边界](#身份与授权的边界)。初版 channel 只接私聊 DM，外部群聊留到后续。具体身份键、核验方式和凭据安全通过技术调查及业务契约落实。
2. **多端投递与可见内容。** 已确认 channel 接入时选择一个 Project 下的助理 DM，同一 DM 的入口共用历史与上下文，回复与主动通知向该 DM 当前可发送的所有已绑定 channel 分发，来源不决定回复去向。查询范围、主动通知工作范围、四类通知及汇报节奏保持已确认规则。绑定的新建及切换流程、离线入口重连后的补发及委派操作的具体范围仍需落实，不能超出 Human 既有权限。群内可见内容随后续外部群聊范围另行设计。
3. **工作变更的确认交互。** 首期询问模式、Sprout 与飞书两端直接确认、同一提案跨入口重复确认只提交一次、目标或操作变化后重新确认已经确定。保守和激进模式留到后续。提案展示、具体确认输入方式、记录及并发去重通过业务契约和交互设计落实。语音以后复用同一份提案和确认记录。

每 Human 一个默认助理和会话接续方式可随上述讨论确定。助理使用独立 Agent profile，单独定制模型与 effort，Chat 归属 Project 并复用普通 Agent Chat，这些方向已确认。具体入口、默认助理的创建及选择、所属 Project、能力配置字段与人设定制范围按[原生入口方案](#原生入口与普通-agent-chat-的复用)及[响应配置](#独立-agent-与响应配置)继续设计。本文中的建议都没有因为写入文档而自动获批。

这些决定确认后，再补共享业务契约、首期页面方案和可执行验收场景，接入总计划、功能计划与 UI 计划。不预先承诺共享一套 runtime、某个数据库结构或特定语音框架。
