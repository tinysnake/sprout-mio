# 前端设计基线

状态：本文约束后续前端设计与实现，归纳已经确认的 UI 基础与 P1/P2 设计。约束生效不代表现有页面已经符合设计，也不代表 I-P1/P2 已通过验收。开发调度从 [开发总计划](development-plan.md)进入，实现规则见 [前端开发约定](frontend-conventions.md)。

## 设计由仓库维护

后续设计、演示与正式实现以仓库为工作入口，不依赖 OpenDesign、MCP、个人应用目录或某个工具的在线状态。OpenDesign 的现有产物作为迁移参考归档，不再作为持续开发和验收的必经环节。

设计依据按职责划分：

| 依据 | 维护内容 |
| --- | --- |
| 产品决策与 `core-scope.md` | 业务范围、术语、身份、权限与生命周期 |
| 本文 | 已确认的视觉、布局与交互规则 |
| `src/theme.css` | 生效的基础与语义 token 数值、主题及 Tailwind 映射 |
| 仓库共享组件及其演示场景 | 组件结构、变体和可操作状态；只有经核对符合本文的实现才成为复用基线 |
| 章节交付记录 | 设计版本、截图、交互验证、已知限制与 Human 确认 |
| `design/archive/` | 历史原型源码；用于追溯，不是可继续扩展的第二套 UI |

存在冲突时按冲突的职责修正，不能因为旧代码或原型里存在某个写法就把它认作设计决定。尤其不能把原型继承的 Cursor 模板说明、营销字体、额外色板和示例业务数据提升为 Mio 规范。现有 shadcn 默认样式也不是已确认的 Mio 组件规范。

## 视觉语言

应用是以 Chat 为主的协作工作区。采用暖中性色、紧凑但可阅读的信息层级、细分隔和少量橙色强调。避免为普通内容逐项套卡片，用区域、文字层级和间距组织信息。

- 基础色板为暖底 `#f2f1ed`、暖近黑 `#26251e`、品牌橙 `#f54e00`。这些是识别基线；代码只在 `src/theme.css` 定义数值，组件读取语义 token。实际主内容背景是派生值，不应直接拿基础暖底替代。
- `background` 用于主内容，`sidebar` 用于侧栏，`secondary` 用于次级区域，`popover` 用于浮层，`hover` 与 `selected` 分别表达悬停和选中。`accent` 是品牌橙，不是 shadcn 常见的浅色悬停背景。
- 主要操作使用 `primary` / `primary-foreground`。原色橙配白字对比度不足，不能把 `primary` 简化成 `accent`。正文链接默认使用可读文字色和下划线；不要把所有链接和小字染成橙色。
- 状态使用 `status-*`，颜色同时配文字或符号，不用品牌色表达所有状态。错误使用 destructive 语义，破坏性操作不能只靠颜色与普通操作区分。
- 浅暗主题沿用相同结构和语义名，在 token 层覆盖颜色。禁止每个页面各自建立浅暗色板。
- 正文和标题使用已安装的 Geist Variable，中文回退 PingFang SC / Microsoft YaHei / sans-serif。代码与标识符才使用 monospace。禁止从旧模板引入 serif、CursorGothic 或新的字体体系。
- 图标统一 lucide-react，常规尺寸 16px、strokeWidth 1.5；大小随组件变体调整，不能逐页更换图标家族。交互图标有文字名称或 accessible name。
- 控件圆角 6px，普通表面 8px，较大容器 10px，分别使用对应语义 token。禁止凭感觉给每页另配圆角、阴影和渐变。
- 间距优先采用 4px 基础节奏及 Tailwind 现有刻度。1–2px 的边框和光学对齐可以局部调整，不需要为每个像素增加 token。
- 复用组件确定字号、行高、密度和控件高度；迁移时从对应原型提取实测值，写入组件变体和演示。原型模板里的 hero 字号不是应用字号基线，不能凭空补一套数字作为“已确认”。

不新增营销 landing page、终端美学、装饰性大渐变、与业务无关的统计卡片或 lorem ipsum。常规动效只用于状态反馈，避免持续装饰动画，并尊重 prefers-reduced-motion。

## 导航与页面组织

- 一级入口只有 Projects、Agents、Machines、Management。Chat 与项目内 Info Hub 属于 Project 上下文，不新增 Feed、独立 Info Hub 或 Task 一级入口。
- 不设置全局 header。普通管理页使用共享页面标题区，由返回入口、一个页面 h1、必要说明和页面操作组成；仅在有实际返回目标或说明时显示对应内容。Chat 保留自己的上下文工具栏。
- Projects 是侧栏二级菜单的折叠开关，不是点击即跳转的页面入口。折叠不改变当前 URL。
- 当前二级菜单只有 Chats、Members、Project settings；桌面和手机保持一致。Project 选择器提供切换和创建，不提供“查看全部 Projects”。
- `/projects` 是入口分发点：零个 Project 显示创建入口，一个进入该 Project 的 Chats，多个才显示列表。多 Project 列表可由 URL 直接进入，不额外添加导航入口。
- 没有独立 Project 详情页。Project ID、创建时间等基本事实并入 Project settings；Project 根地址进入 Chats 上下文。具体正式 path 由路由实现和交付矩阵记录，不照搬原型 hash。
- 注册时尽力创建“我的项目”和 Amenda（职位“全能秘书”）；新建普通 Project 不自动添加 Agent。默认创建失败后的零 Project 入口必须可用。
- 职位字段为 `jobTitle`，可空、最多 40 字、只展示分工、无权限语义；空值不显示职位徽标。`role` 保留给二期权限。model 与 effort 的空值表示使用宿主默认，不能编造可用模型选项。
- 一期没有 Project 删除。不得为凑齐操作菜单添加删除入口或假实现。

## Chat 与响应式

布局优先保住导航与列表可达性，然后分配 Chat 和 inspector 的空间。Inspector 面向宽屏；不足宽度时不能通过挤没列表来保住 inspector。

| 视口 / 状态 | 已确认行为 |
| --- | --- |
| 宽度 ≥1200px | 桌面工作区，侧栏默认 200px；列表、Chat 与打开的 inspector 并排；允许手动收起侧栏 |
| 901–1199px | 保留桌面列表与 Chat；打开 inspector 时侧栏自动收为 64px 图标栏，列表继续保留 |
| 接近 901px 且 inspector 打开 | 列表向 160–180px 收缩，不能先隐藏列表；Chat 允许缩小 |
| 宽度 ≤900px | 列表、Chat 详情和信息视图分屏切换，保留明确返回入口；一级和二级导航语义不变 |

- 常规桌面列表随可用空间在约 220–272px 调整。Inspector 默认约 320px、最小约 240px；可拖拽宽度上限由布局约束计算，不能把中心内容挤出屏幕。迁移保留现有拖拽与键盘调整行为并验证边界。
- 列表过窄时隐藏类型筛选 tabs，不改成下拉框；隐藏后类型条件停止过滤，不能保留用户无法发现和解除的筛选。搜索条件独立处理。
- 列表、消息区、inspector 各自滚动，布局容器正确设置 min-width / min-height 与 overflow，长名称、长 ID 和长消息不能撑出整页水平滚动。
- 手机输入区考虑动态视口和 safe area。不得因样例消息较短就省略输入区与软键盘验证；模拟视口不能作为真机软键盘证据。
- 同一目标在桌面、手机、刷新、直接打开和前进后退时含义一致。Inspector 的恢复方式由明确的 URL 或状态约定表达，不能只靠上一个页面留下的对象。
- 不擅自删掉目前保留的三处 run 状态。状态的合并与信息取舍属于体验调整，需要有明确决定。

以上 900px 和 1200px 是产品布局边界，不能因为 Tailwind 默认断点更方便就改成 768 / 1024 / 1280px。实现应由共享布局拥有断点；组件内部密度可按容器空间调整。

## 状态、反馈与可访问性

- 保存、创建、移除、发送等操作具备 pending、防重复提交、成功反馈与失败恢复。只有服务确认成功才展示成功，失败保留用户输入并可重试。
- Agent profile 保存提示下一轮生效，不暗示当前轮已读取新配置。刷新和重新进入后以服务端事实为准。
- 空数据、加载、失败、无权访问、未实现、断线、旧数据和未知是不同状态；按实际契约展示，不为页面机械补满状态。
- 未实现功能明确使用灰色说明，例如“未实现，P4”，不放假 Machine、假租约和假 Task。已经存在的 P3 能力不能被换成未实现占位。
- 导航使用 link，状态变化使用 button；折叠按钮维护 aria-expanded，当前页维护 aria-current。可关闭的浮层支持 Escape、焦点进入与关闭后返回触发点。
- 输入有 label，错误关联字段；图标按钮有名称。键盘焦点可见，菜单、弹窗与拖拽分隔条可用键盘操作。
- 正文和普通文字目标对比度至少 4.5:1，大字至少 3:1；用于识别交互控件或状态的必要视觉边界至少 3:1。纯装饰性分隔线不机械要求 3:1，输入边框是否通过须结合实际控件识别方式检查。

## 已知限制与更改规则

现有对比度审计里部分输入边框低于 3:1；disabled 按钮对比度的调整已延后。手机导航未实现标签换行、Members / Settings 内容宽度、真机软键盘和拖拽手感仍需核对。这些不是以后新增问题的豁免，也不能宣称已经全部符合可访问性要求。

沿用既有组件组合、补齐业务要求的状态、修复符合本文的细节，可直接实施并验证。改变导航层级、布局边界、品牌与字体、全局密度、共享组件语义或业务状态含义时，先在任务里写明原规则、具体改法与受影响页面；新的设计方向保留待 Human 确认，不自行宣布定稿。已有明确授权的改动直接执行，不重复索要批准。

新增场景优先扩展已有组件变体。确实需要新增组件时，说明现有组件缺什么，并同步共享演示和本文涉及的规则。设计决定、实现完成、技术验收和 Human 体验确认分别记录。
