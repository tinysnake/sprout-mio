# 自动化决策草案

> 状态为产品讨论草案。本文记录已确认的方向、建议和待定项，不表示能力已经实现，也不替代开发计划、业务契约或验收记录。

## 讨论状态

本次讨论在一期交付之后展开。一期实现与验收以[开发总计划](development-plan.md)和[一期归档](archive/phase-one/README.md)为准。

本文区分以下状态。

- **已确认**表示 Human 已在本轮讨论中接受的产品方向。
- **首版默认**表示按 Human 授权由执行者直接选择的首版行为，允许在验证后调整。
- **建议**表示草案提出的候选方案，仍可调整。
- **待定**表示通过技术调查或业务契约需要补齐的决定；不意味着每一项都需要 Human 再次确认。

已确认的是产品方向。Webhook 首版字段、API、并发边界及专项验证已落实，见[Webhook 契约](webhook-core.md)与[功能地图](feature-map/automation.md)。Cron 和其余扩展仍按本文区分讨论状态。个人助理、身份及 channel 的共同边界见[个人助理与 channel 决策草案](personal-assistant-decisions.md)。

## 已确认的目标与范围

自动化服务于外部事件触发、周期性检查和减少手动操作。Human 可以配置 webhook 和 cron，使 Sprout 在指定上下文中接受工作，并能查看结果。

首期方向已确认如下。

- Webhook 与 cron 规则都配置在 Project 内，Project 是规则的上层结构。规则的归属与触发动作分开配置。
- 由 Human 创建、修改和启停自动化配置。首期不开放 Agent 自行管理规则。
- 触发动作可配置。首期主要向同一 Project 内的 DM 或 Group 发送系统来源消息，唤醒 Agent。内置系统动作留到后续。
- 消息目标失效或目标不是可唤醒的 Agent 时，本次触发不执行并记录原因，不自动寻找其他 Agent 替代；后续触发仍按原规则重新检查目标。
- 使用正常持续运行的服务环境。服务离线时不执行，不建设离线补偿队列。
- 定时能力先做 cron。不做一次性倒计时，暂缓更丰富的日历交互。
- 同一 cron 规则的上一次工作尚未结束时，跳过本次触发并记录原因，不排队、不并行启动该规则的另一份工作；被跳过的时点不补跑。
- 先采用简单、可解释的可靠性机制。失败有记录，可以由 Human 处理，不建设复杂恢复系统。
- Channels 必须模块化，先实现飞书。Channel 的对话与身份能力由个人助理领域承接。
- webhook 和 cron 可以直接提交已配置的工作，不必先调用助理 LLM。助理可以观察工作，并在配置允许时通知 Human。

本文先按入站 webhook 讨论外部事件接入。通用出站 webhook、复杂工作流、运行时插件市场和更多聊天平台不计入当前首期方向。日历交互暂缓不等于删除 cron 本身的日期与星期表达能力。

## 现有能力与新增能力的边界

现有 Chat 是 Project 内的持久协作单元。Task 与 run 有各自的生命周期，不能把每次外部事件都直接等同为创建 Task 或立即启动 run。相关约束沿用[通信决策](communication-decisions.md)与[Tasks 决策](tasks-decisions.md)。

现有 [`chat-schedule.ts`](../src/domain/chat-schedule.ts)处理消息及 `task_periodic` 评估、claim 和 lease。这不是面向 Human 配置的日历 cron。新增定时入口需要明确自己的规则与触发记录，再接入现有协作能力。

现有[聊天消息合同](../src/contracts/chat.ts)的发送者只有 Human 或 Agent，尚未表达自动化的系统来源。[通信决策](communication-decisions.md)已有显式点名与 Group 唤醒规则，但不能据此声称自动化系统消息已实现。新增来源如何进入消息历史、上下文与路由仍需补契约。

外部触发不能绕过 Project 访问、Agent 成员资格、分身串行执行和 Machine 租约规则。Webhook 请求者不能通过 payload 临时指定任意执行身份或扩大工作范围。

## 讨论中的对象关系

这些对象描述产品关系，不预设数据库表或 API 形状。

| 对象 | 含义与边界 | 状态 |
| --- | --- | --- |
| 自动化规则 | 归属于一个 Project，由 Human 保存触发条件、触发动作及所需配置 | 已确认方向，具体字段待定 |
| 触发来源 | 首期为入站 webhook 或 cron；两者保留各自的认证、时间与事件语义 | 已确认 |
| 触发动作 | 首期向所属 Project 内的 DM 或 Group 发送系统来源消息并唤醒 Agent，后续可扩展内置系统动作 | 已确认方向，动作契约待定 |
| 消息目标 | DM 的唯一 Agent，或 Group 中明确 @ 的 Agent、当前 Agent owner；目标属于规则所在 Project，失效时不自动替换 | 已确认方向，校验契约待定 |
| 触发记录 | 说明哪条规则因何触发，以及输入是否被接纳、拒绝或跳过 | 建议 |
| 工作关联 | 将已接纳的触发关联到消息及后续工作，保留与 Task、run 的区别 | 建议 |
| 结果投递 | 将工作结果发送到已配置的接收位置，与工作执行结果分开记录 | 已确认方向，接收位置与首期范围待定 |

一次工作可以有多个投递尝试。投递失败不能自动变成再次执行工作。Human 重发结果与重新执行工作需要是两个不同的操作。

## Project 归属与可配置的触发动作

**已确认。** Webhook 与 cron 规则的上层结构是 Project。Human 在 Project 内管理规则，再配置该规则触发什么动作。消息目标限于所属 Project，不允许外部 payload 临时改到其他 Project、Chat 或执行身份。

首期主要提供发送系统来源消息并唤醒 Agent 的动作。

| 目标 | 动作语义 |
| --- | --- |
| DM | 向该 DM 的唯一 Agent 发送配置的提示内容，唤醒对应分身 |
| Group 中指定 Agent | 向 Group 发消息并明确 @ 接收 Agent，唤醒对应分身 |
| Group owner | 向 Group 发消息，交由当前 Agent owner 接手并组织后续工作，不要求配置固定成员 |

本文 DM 对应本轮讨论中所称的 DDM，沿用现有 Chat 术语，不新增对话类型。Group owner 可以是 Human 或 Agent，Human owner 不能作为可唤醒的 Agent。

**已确认。** 触发时目标失效或目标不是可唤醒的 Agent，例如指定 Agent 已被移出 Group，或 Agent owner 已换为 Human，则本次触发不执行并记录原因，不自动寻找其他 Agent 替代。规则不因此自动停用或改写目标，后续触发仍按原规则重新检查，目标有效时正常执行。选择当前 owner 的动作始终按当前 owner 判断；显式指定的 Agent 不因成员变化而自动替换。

**已确认。** Agent 收到的消息必须明确标识为系统触发，不能伪装成 Human 手动发言。内容可包含 Human 在规则中配置的提示词、定时任务信息，以及 webhook 传入的数据。系统来源标识由程序产生，保留规则与触发来源，不由外部正文自行声明。

这里的系统来源描述消息的来源与用途。模型消息角色、上下文注入和历史呈现由后续契约落实，不在本文预设具体 SDK 调用。Webhook 数据仍是外部输入，不因置于系统来源消息中而获得额外权限。

**后续方向。** 触发动作可扩展为直接调用系统内置功能，例如重启。当前不实现这些动作，不开放任意系统命令。首期动作数量、一次触发能否组合多个动作及具体配置字段尚未冻结。

消息投递沿用既有分身串行与 Human 控制边界。唤醒不保证立即启动新的 run，也不要求每次触发创建 Task。Group 的显式 @ 与交由 owner 接手是需要表达的动作语义，具体接入现有消息路由的方式留待业务契约确定。

## Webhook 的首期方向

**已确认方向。** Human 为外部事件配置入口、认证和固定工作上下文。入口需要基本去重，避免同一个事件因发送方重投而重复安排工作。

**建议。** 请求边界先完成认证、输入校验、去重和工作接纳，再返回接纳结果。HTTP 请求不等待 Agent 完成。未经认证、规则停用、目标失效和内容不受支持的请求应有可区分的处理结果。

**建议。** 初期只提供有限的事件筛选和内容映射。外部文本作为待处理内容，不能直接变成任意代码、工具名或权限配置。不要为首个接入引入通用表达式引擎。

需要在技术调查与业务契约中明确以下问题。

- 认证采用共享密钥还是提供方签名，如何轮换凭据。
- 使用哪个来源标识和事件 ID 去重。发送方没有稳定 ID 时，哪些有限保证仍可提供。
- 去重保留期、请求大小、内容类型和快速响应的具体限制。
- 配置修改后，已接纳的触发继续使用哪个版本的目标与内容。

服务离线期间，Sprout 不主动补拉事件或重放历史。发送方可能自行重试；重启后收到的请求属于新的入站处理过程。是否接纳过期事件及如何判断过期仍需定规则，不能把“不补做”解释为发送方一定不会重投。

## Cron 的首期方向

**已确认方向。** Human 使用 cron 表达式安排周期性工作，服务离线期间错过的执行不补做。

**建议。** 每条规则显式保存时区，界面展示下一次计划时间、启停状态和最近执行结果。不能让服务器默认时区静默改变 Human 的日程。

Cron 只决定何时提交工作。后续执行仍沿用工作 Chat 与分身的规则，不因定时触发而获得额外并发或执行权限。

**已确认。** 同一规则的上一次工作尚未结束时，跳过本次触发并记录原因，不排队、不并行启动该规则的另一份工作。被跳过的时点不补跑，上次工作结束后按后续计划时点正常触发。例如每 5 分钟触发、首次工作用时 8 分钟，则第 5 分钟跳过，第 10 分钟正常触发。

以下技术行为在业务契约中核定。

- 系统在线但调度延迟时，怎样判断一个时点已经错过。不要将普通延迟与服务离线混为一谈。
- 夏令时切换时，不存在或重复的本地时刻如何处理。

手动试运行纳入首版默认值，见[首版默认行为](#首版默认行为)。

表达式方言和秒级支持应通过候选库与实际场景调查确定。业务契约需要公开所选语义；不能只依赖库的未说明默认值。

## 执行、通知与简单可靠性

**已确认方向。** 工作完成和结果送达是两个不同事实。结果发送失败时，保留工作结果，不为重发通知重复执行工作。

**建议。** 触发记录至少让 Human 看清以下区别。

- 来源未被接纳，例如认证失败、规则停用或目标已失效。
- 来源被跳过，例如重复事件或按策略跳过重叠的 cron 时点。
- 工作已接纳，并可追踪到已有协作对象。
- 工作结束后，结果已送达或发送失败。

服务退出、网络错误或结果不确定时，首期允许保留可见的失败或不确定记录，由 Human 检查。基本去重不等于端到端恰好执行一次，首期不作这种保证。

**建议。** 规则停用阻止后续接纳，不隐式取消正在运行的工作。删除配置不删除工作历史。最终行为需要随生命周期契约一起确认。

简单可靠性不排斥保存必要的触发与投递记录。记录用于说明发生了什么，不意味着承诺离线重放或自动恢复。

## 与个人助理及 channel 的衔接

Webhook、cron 与飞书事件可以复用经过授权的工作提交和结果观察能力，但各自保留来源语义。飞书自然语言对话不应被压成普通 webhook 模板。

自动化规则按已批准配置执行。个人助理发起的新工作则需要经过其提案与授权机制。两者都要保留谁配置、谁请求、实际由哪个工作分身执行的来源信息。

结果可以进入助理通知能力，是否纳入主动通知遵循[个人助理的通知范围](personal-assistant-decisions.md#通知与多个入口)。已确认助理消息统一向消息所属助理 DM 当前可发送的所有已绑定 channel 分发，来源不决定回复去向。各 channel 的绑定、发送能力与投递结果由程序分别检查和记录，不以“Human 最近使用的 channel”选择唯一目的地。该规则适用于进入助理通知能力的结果，不隐式改变自动化规则中其他独立投递动作的配置。

没有可用 channel 时，助理可以保留待通知事项。这个行为与 cron 离线不补做属于不同规则。

## 用于细化契约的场景

下列场景表达应讨论和验证的行为，不表示已经写成或通过验收脚本。带建议的行为在 Human 确认后才能成为冻结的验收要求。

1. 已认证事件到达，按保存的目标接纳工作。相同事件 ID 重投时，不重复安排同一工作。
2. cron 到点后提交工作。服务离线错过若干时点，重启后只安排未来时点，不集中补做历史工作。
3. 工作已经完成，但飞书发送失败。Human 重发结果时，原工作不再次执行。
4. 目标 Chat 归档、成员资格撤销或来源认证无效时，外部输入不能恢复已经失去的权限。
5. Human 暂停规则后，新的事件不再触发。已经提交的消息不撤回，已启动的工作继续进行，需要停止时使用 Chat 中已有的停止操作。
6. 两条规则指向同一工作分身时，仍遵守现有的执行串行与资源约束。
7. 同一 cron 规则每 5 分钟触发，首次工作运行 8 分钟。第 5 分钟的触发被跳过并记录原因，不排队或补跑；第 10 分钟按计划正常触发。
8. Human 在一个 Project 内创建规则并配置 DM 消息动作。触发后，唯一 Agent 收到配置内容及明确的系统来源标识，能够与 Human 手动消息区分。
9. Group 消息动作配置显式 @ 时，唤醒所指定的有效 Agent。配置由 owner 接手时，消息交给当前 Agent owner，由它组织后续工作。
10. Webhook payload 尝试替换 Project、Chat、接收 Agent 或伪造 Human 身份时，不能覆盖规则中已授权的目标与真实来源。
11. 指定 Agent 已被移出 Group，或规则要求唤醒的当前 owner 已变为 Human。本次触发不执行并记录原因，不寻找其他 Agent 替代，不自动停用规则；后续触发按原配置重新检查目标。

## 首版默认行为

以下为本轮授权范围内由执行者确定的首版默认值，不作为新增的 Human 逐项确认记录。容易修改的选择直接落实；返工成本较高的边界在业务契约中先核对，遵循[早期版本的决策方式](project-conventions.md#早期版本的决策方式)。

| 事项 | 首版行为 |
| --- | --- |
| 停用规则 | 只阻止新的触发，不撤回已提交的消息，不停止已启动的工作。停止当前工作使用既有 Chat 操作 |
| 修改规则 | 新触发使用新配置，已接纳的触发保留当时配置与来源。实际执行仍检查当前权限和目标有效性 |
| 动作数量 | 每条规则先配置一个消息动作，不提供动作链、条件分支或工作流编辑器 |
| 手动试运行 | 提供显式试运行，真实提交消息并标识为试运行，不推进 cron 的下一计划时点，不绕过权限、目标与重叠检查 |
| 查看记录 | 在所属 Project 内查看规则及触发记录，展示接纳、跳过、失败原因，并可跳转关联的工作 Chat 和运行记录 |
| 主动通知 | 自动化触发不自动扩大个人助理的关注范围。未被关注的工作通过触发记录与 Chat 查看；已被关注的仍按助理通知规则处理 |
| Cron 输入 | 先使用分钟级五段表达式，明确保存时区并展示下一触发时间。时间方言、夏令时与在线调度延迟语义通过所选库的实际行为落实到契约，不逐项向 Human 提问 |
| 结果重发 | 重发投递与重跑工作分开；首版不建设复杂自动重试和补偿系统 |

规则停用与已接纳工作分开处理已得到 Human 明确认可。该原则也适用于配置修改，不通过编辑规则隐式干预工作 Agent。

## 下一轮决定与后续文档

优先完成 Project 内的自动化消息闭环，再接入[个人助理](personal-assistant-decisions.md)与飞书。Webhook 和 cron 不依赖助理 LLM，通知衔接遵循已确认的关注范围。

Project 归属、可配置动作及首期 DM 和 Group 消息唤醒方向已确认。Cron 重叠处理已确认按同一规则跳过并记录，不排队或补跑。目标失效或所选 owner 目标为 Human 时，本次不执行并记录原因，不自动换 Agent，后续触发继续按原规则检查。首版默认行为见上节，不再逐项请求 Human 确认。

下一步补业务契约与可执行验收场景，再落实功能和 UI 单元。消息来源、触发与运行的关联，以及 Group 工作结束的判定涉及多个模块，先核对现有调度与续跑生命周期。认证算法、cron 库及事件 ID 通过技术调查选择。若出现必须改变已确认行为或需要昂贵迁移的取舍，再集中向 Human 说明。当前不预设完整群聊协作追踪或通用工作流系统。

本文不分配新阶段编号，不把默认选择当作已经实现或验收通过。
